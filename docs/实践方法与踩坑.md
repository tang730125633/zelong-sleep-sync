# 从真实问题出发，做一条能验证的同步链路

## 1 · 先区分“没有数据”和“没有上传”

网站没有更新，不代表手表没有记录

先看服务端最后一次收到请求的时间
再看睡眠、活动、训练是否同时停更
最后回到手机，检查导出有没有触发

如果服务器根本没收到请求
改网页、改数据库，都碰不到问题的起点

## 2 · 先跑通最小闭环

最初想一次读取多项健康指标
实际遇到了运行时间、权限和设备来源问题

后来先收窄到睡眠
原生读取 → 上传 → 保存 → 查询
先让一条真实数据走完，再扩大范围

这也是当前仓库只承诺睡眠同步的原因

## 3 · 原生功能已经有的，不再造一遍

健康读取交给 iPhone 的快捷指令
触发条件交给系统自动化
数据保存采用 SQLite
AI 查询复用同一个数据库

不需要为了“打开微信时执行”去开发微信机器人
也不需要先做一个完整 iPhone App

## 4 · 文件生成正确，不代表真机运行正确

这次遇到的几个具体问题：

| 问题 | 处理方法 |
| --- | --- |
| 日期筛选导入后无效 | 使用真机支持的 between 条件，内部编号 1003 |
| 日期参数无法正确传递 | 日期输入使用 token string，输出 ISO 8601 并带时间 |
| 循环拿到整批结果 | 使用 Repeat Item，不能拿循环开头的 ActionOutput 代替 |
| JSON 批次为空 | Combine Text 的输入键是 `text`，不是 `WFInput` |
| 中文分期无法识别 | 补充快速动眼睡眠、清醒时间等标签 |
| 系统没给设备来源 | 明确标注未知来源，不假装它来自 Apple Watch |
| 整批历史记录无法分享 | 按时间窗口分批，不把放宽隐私设置当默认解法 |
| 镜像粘贴内容不对 | 核对手机输入框，不能假定 Mac 和手机剪贴板相同 |

这些是本次环境里验证过的做法
iOS 变化后仍需要重新检查，不能把内部格式当永久承诺

## 5 · 去重解决的是“重复动作也安全”

打开微信可能一天发生很多次
上传动作重复，不应让睡眠时长跟着累加

按日期和来源比较旧记录
相同内容跳过，有变化再更新
分期修正时替换覆盖区间，避免留下旧边界
在同一个事务里保存数据与同步状态

不完整的首晚不能覆盖完整旧记录
缺失不等于零，清醒不算睡眠

## 6 · 成功必须有证据

一共核对三处：

1. 手机拿到成功回执
2. 服务器出现新的成功接收时间
3. 网站和 MCP 能读到保存后的数据

弹出通知，只能证明任务开始或触发
只有保存完成，服务端才返回成功结果

`imported` 是处理记录数
`changed` 是本次变化数
它们都不是“睡了多少天”

## 7 · 把项目能力和验证范围分开写

原项目完成了真机睡眠上传、微信触发与 MCP 读取
独立版本抽出了同样的处理逻辑
新的 HTTP 外壳通过了合成数据端到端测试

这不等于所有 iPhone、所有 iOS 都已验收
更不等于步数、心率和训练都已经完成

一个可信的作品集应该能回答：
做了什么，为什么这样做
怎样知道它成功了
还有哪些地方没完成

## 这套方法可以复用到哪里

任何“设备数据 → 私有服务 → AI 查询”的小项目
都可以先沿着同样的顺序检查

先定位数据断在哪里
再做一个最小可验证闭环
最后处理重复执行、权限和错误反馈

别让界面上的“成功”，代替真实结果
